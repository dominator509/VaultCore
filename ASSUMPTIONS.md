# Assumptions

The assumptions below are the minimum safe assumptions made while generating this blueprint. Every assumption derives from the uploaded Architecture.md, THREAT_MODEL.md, and TRACEABILITY.md, or from explicit defaults required to avoid hallucination.

| ID | Assumption | Reason | Risk If Wrong | How to Verify | Blocks Implementation |
|---|---|---|---|---|---|
| A-001 | VaultCore is a greenfield repository; no prior source code exists. | Architecture.md describes intended layers and Trinity contract but no implementation evidence; TRACEABILITY.md statuses are all PLANNED. | Existing patterns may be overwritten or duplicated. | Run EP-000 inventory; confirm no `src/`, `crates/`, or `app/` exists before EP-001. | Yes |
| A-002 | Builder and Verifier are separate Rust processes communicating over a signed local IPC channel (Unix domain socket on macOS/Linux, named pipe on Windows). | Architecture.md requires Trinity process boundary (I-4) but does not name the IPC mechanism. | A different IPC choice may affect threat surface and tests. | Confirm in EP-001 Decision Log; record final choice in ADR-0005. | No (smallest reversible choice) |
| A-003 | UI uses TypeScript + React inside a Tauri shell. | Architecture.md names L1 Experience as TypeScript; Tauri is the smallest reversible choice that pairs Rust core with TS UI without bundling a full browser engine differently. | A different shell (Electron, native) would change build, packaging, and threat surface. | Confirm during EP-001; record in ADR-0006. | No |
| A-004 | Persistence uses SQLite with payload columns holding only opaque ciphertext blobs. | Architecture.md L6 references encrypted persistence and audit; SQLite is the simplest local store satisfying I-1 and I-3. | A different store (sled, RocksDB) would change repository and migration design. | Confirm during EP-003; record in ADR-0007. | No |
| A-005 | Payload AEAD is XChaCha20-Poly1305; key derivation is HKDF-SHA-512; passphrase KDF is Argon2id; signatures are Ed25519. | Architecture.md envelope formats reference these primitives. | Wrong algorithm would invalidate threat-model mitigations. | Verify in EP-002 against Architecture.md "Envelope Formats" section; lock in ADR-0008. | Yes (if mismatched) |
| A-006 | WebAuthn passkeys are the preferred auth path; biometrics and Argon2id-derived passphrase are fallbacks. | Project brief and threat model emphasize phishing-resistant local auth. | Wrong path order could weaken anti-phishing posture (T-007). | Confirm in EP-006; record in SPEC-005. | Yes |
| A-007 | The five roles (Owner, Admin, Editor, Viewer, Auditor) and eight secret types (API_KEY, LOGIN, OAUTH_APP, SSH_KEY, WALLET_KEY, CERT, NOTE, BLOB) are exhaustive for v1. | Project goal mandates strict scope; THREAT_MODEL.md scopes mitigations to these. | Adding more would invalidate scope, tests, and threat coverage. | Verify in SPEC-001 and SPEC-005. | Yes |
| A-008 | Secret lifecycle FSM is exactly: draft → active → expiring_soon → expired → rotating → archived → soft_deleted → purged. | Architecture.md L4 references this state machine. | Wrong FSM breaks rotation, retention, and audit logic. | Verify in SPEC-001 and EP-002. | Yes |
| A-009 | Audit log is append-only and hash-chained (each entry contains prior_hash + payload_hash). | Invariant I-8 and Architecture.md require tamper-evident audit. | Wrong structure breaks tamper evidence and gate G1-F. | Verify in EP-003 and SPEC-007. | Yes |
| A-010 | No remote server, no telemetry, no auto-unlock-from-cloud path in v1. | Invariant I-7 forbids vendor backdoor; project brief excludes cloud sync. | Adding any would violate I-7 and project scope. | Locked by AGENTS.md STOP condition for any code path that introduces remote network calls without an approved ADR. | Yes |
| A-011 | MSTest-equivalent in TypeScript context is Vitest; Rust tests use `cargo test` + `cargo nextest`; E2E uses Playwright. | Repository facts: MSTest is the user's confirmed unit-test framework convention; Vitest is its TS equivalent. | Different runners change `COMMANDS.md` and CI parity. | Verify in EP-001; lock in ADR-0009. | No |
| A-012 | Production deployment means a signed Tauri bundle distributed to the user; there is no production server to deploy. | Project deploys as a desktop app. | If misread as a service deployment, runbooks would be wrong. | DEPLOYMENT.md and RELEASE.md must explicitly handle desktop signing. | No |
| A-013 | The eight invariants I-1..I-8 listed in Architecture.md are exhaustive for v1 enforcement. | Architecture.md enumerates them; THREAT_MODEL.md maps mitigations to them. | Adding undocumented invariants risks unverifiable scope. | EP-010 must check every invariant has at least one enforcement test. | Yes |
| A-014 | Residual risks R-1..R-5 in THREAT_MODEL.md are accepted by the project owner as documented. | THREAT_MODEL.md marks them residual. | Treating them as unaccepted would block production. | DEPLOYMENT.md and PRODUCTION_READINESS.md must surface them in the launch checklist. | No |
| A-015 | All scripts are POSIX `sh`-safe for macOS/Linux; Windows uses a parallel `*.ps1` shim added in EP-009 if and only if required by CI/CD. | Blueprint scripts default to `#!/usr/bin/env sh`. | Windows-only contributors may need PS shims. | EP-009 confirms or adds PS shims; record in ADR. | No |
